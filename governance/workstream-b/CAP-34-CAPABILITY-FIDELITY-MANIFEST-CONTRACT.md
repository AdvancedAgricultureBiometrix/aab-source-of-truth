# CAP-34 Capability Fidelity Manifest Contract

**Contract version:** 1.0.0  
**Status:** CONTROLLED SIMULATION DISCLOSURE CONTRACT  
**Authority:** Disclosure only — no production, scientific, regulatory or commissioning authority

> **Complete simulator coverage does not mean complete product implementation.**

## Purpose

The Capability Fidelity Manifest is the authoritative truth structure for what CAP-34 represents at a particular point in time.

It prevents a complete-looking simulator from being mistaken for a completely implemented AAB product.

The manifest precedes and governs the Roadmap Preview acknowledgement receipt. A receipt may reference a manifest snapshot; a receipt must not define capability truth.

## Versioning model

CAP-34 uses **per-capability representation versioning rolled into an immutable whole-manifest snapshot**.

### Capability representation version

Each capability entry has its own `representationVersion`.

Increment it only when that capability's simulator representation materially changes, including:

- fidelity classification;
- simulator mode;
- scenario coverage;
- implementation/evidence reference;
- material limitation;
- disclosure burden;
- represented scope.

A change to CAP-14A does not require unrelated capability representation versions to change.

### Manifest snapshot version

Every published manifest state receives a unique immutable `manifestSnapshotId` and `manifestVersion`.

A snapshot binds the complete ordered set of capability entries and their exact representation versions/classifications at that time.

The future disclosure receipt will reference the snapshot plus the exact capabilities shown. Historical snapshots are immutable.

## Required fidelity values

Exactly one:

- `REAL_LOGIC_SYNTHETIC_REFERENCE_DATA`
- `PARTIAL_REAL_LOGIC_LIMITATIONS_SHOWN`
- `CONCEPT_PREVIEW_NOT_IMPLEMENTED`
- `NOT_YET_REPRESENTED`

Human-readable labels must preserve the canonical wording.

## Required simulator modes

- `LIVE_SIMULATION`
- `ROADMAP_PREVIEW`
- `NONE`

Rules:

- `REAL_LOGIC_SYNTHETIC_REFERENCE_DATA` requires `LIVE_SIMULATION`.
- `CONCEPT_PREVIEW_NOT_IMPLEMENTED` requires `ROADMAP_PREVIEW`.
- `NOT_YET_REPRESENTED` requires `NONE`.
- partial real logic may use Live Simulation only when limitations are persistently shown.
- Roadmap Preview must never be used to imply behavioural proof.

## Capability entry contract

Every agreed end-product capability must have one entry containing:

- `capabilityId`
- `capabilityName`
- `capabilityPart` where a split such as CAP-14A/CAP-14B matters
- `horizon`
- `representationVersion`
- `simulatorMode`
- `fidelity`
- `scenarioCoverage`
- `implementationReferences`
- `evidenceReferences`
- `limitations`
- `disclosureBurden`
- `lastVerifiedAt`
- `lastVerifiedAgainst`
- `classificationReason`
- `nonImplications`

Unknown evidence must remain unknown. Empty references cannot be interpreted as proof.

## Disclosure burden

Values:

- `STANDARD`
- `HEIGHTENED`
- `EXCEPTIONAL`

The more demo-attractive a capability is, the greater its disclosure burden should be where fluent presentation could materially outrun behavioural proof.

CAP-33 is `EXCEPTIONAL` while it remains Future Platform/unproven.

## Scenario coverage

Scenario coverage is explicit, not inferred. Each entry records zero or more scenario IDs and the level of coverage:

- `FULL_FOR_REPRESENTED_SCOPE`
- `PARTIAL`
- `ILLUSTRATIVE_ONLY`
- `NONE`

A scenario existing elsewhere in CAP-34 does not imply that a capability is covered by it.

## Snapshot integrity

A manifest snapshot must contain:

- `manifestId`
- `manifestVersion`
- `manifestSnapshotId`
- `createdAt`
- `sourceLandscapeReference`
- `capabilityCount`
- `entries`
- `snapshotDigest` when generated by a hashing-capable runtime.

The digest is an integrity aid, not authority.

## Fail-closed validation

A snapshot is invalid if:

- an agreed capability is absent;
- a capability has no fidelity;
- a fidelity/mode combination violates this contract;
- a Roadmap Preview entry lacks explicit limitations/non-implications;
- an entry claims real logic without implementation/evidence references sufficient to support that classification;
- CAP-33 is represented below its required disclosure burden while unproven;
- duplicate capability-part identities exist;
- a representation version is missing.

Validation failure must return `FAIL_CLOSED_MANIFEST_INVALID`.

Successful structural validation returns `PASS_CAP34_FIDELITY_MANIFEST_VALID`.

That status validates manifest structure and internal consistency only. It does not validate the underlying scientific capability, production readiness, sovereignty or commissioning.

## Relationship to future disclosure receipt

The receipt must be downstream of this manifest.

At minimum it will reference:

- exact `manifestSnapshotId`;
- exact `manifestVersion`;
- capabilities actually shown and their `representationVersion`;
- fidelity values presented;
- Roadmap Preview version/entry state;
- acknowledgement wording/version;
- evaluator identity/role permitted for the simulation;
- timestamp and correlation/reference ID.

Receipt design begins only after this manifest contract and initial snapshot are stable.
