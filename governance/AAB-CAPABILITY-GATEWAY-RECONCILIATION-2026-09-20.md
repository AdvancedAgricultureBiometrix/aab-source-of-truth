**Status:** DECISION-SUPPORT DOCUMENT — NOT IMPLEMENTATION
**Authority:** BUILD-PLANNING ONLY. Establishes no commissioning, production, Gate D, WP05, scientific-validity or regulatory authority.
**Subject:** the seven canonical capabilities carried through the CAP-34 governed simulation's "live logic" wiring — CAP-01, CAP-02, CAP-04, CAP-05, CAP-06, CAP-07, CAP-09.
**Not part of PR #16.** PR #16's boundary (`governance/workstream-b/`, `simulation/cap34/`, draft, simulation-only) is unaffected by this document.

## Vendor posture

AAB is vendor-neutral. Supabase is the current rehearsal-bundle provider evidenced in `governance/AAB-current-technical-contract-catalogue-2026-09-20.md`, not a permanent architectural requirement. This document therefore separates two different things that the earlier draft ran together:

- the **provider-neutral service interface** each capability actually needs (what operation must exist — register a source, persist a governed record, submit for human review — regardless of who implements it), and
- the **current Supabase-specific realization** of that interface, as evidenced in the rehearsal bundle today.

A capability's field names and a Supabase action's field names being different is not, on its own, evidence of a problem. It is the normal condition at a provider boundary and is closed with an adapter layer. AAB's canonical field names for its scientific contracts are a governance decision for AAB to make on AAB's own terms; they are not, and must not be inferred from, whichever field names happen to appear in a given provider's rehearsal bundle. Where this document earlier read field-name differences as if they were canonical-schema conflicts, that framing is corrected below.

## Purpose

For each of the seven capabilities, this document states whether the current Supabase-based gateway already realizes the provider-neutral operation that capability needs, and if so how directly:

- **Direct wire** — the provider-neutral operation already has a real, actor-gated, persistent Supabase-backed implementation. What remains is a thin adapter mapping CAP-34's canonical field names to Supabase's provider-specific ones — expected work at any provider boundary, not a sign the match is weak.
- **Translation layer needed** — a Supabase table or action exists that is *closer to* the needed operation than "nothing", but its shape (not just its field names) diverges from the operation CAP-34 actually needs, so more than a name-level adapter is required.
- **New gateway action needed** — no Supabase implementation of the needed operation exists yet, whatever else (schema declarations, browser contracts) may exist. This is a statement about missing implementation, not about vocabulary.
- **Design decision required before wiring** — more than one plausible Supabase-side landing zone exists for the operation, or the operation's scope collides with another capability's, so a decision is needed before any provider-specific wiring — Supabase or otherwise — can proceed.

This document makes no wiring decision itself and does not fix AAB's canonical field names. It records what a provider-neutral read of the current evidence supports.

## Evidence tiers used below

All tiers describe the *current Supabase rehearsal bundle*, not AAB's architecture in general:

1. **Supabase-backed operational action** — an `action` name in the catalogue's HTTP action table with a PostgreSQL callable behind it, reached only through the real actor-resolution path (`agriculture.api_resolve_authenticated_actor`). This is today's realization of a provider-neutral operation, where one exists.
2. **Browser contract** — a JavaScript namespace/function exposing validation, scoring or advisory logic, mostly provider-independent in itself. Several such files carry `failClosed`, `blockOperationalRequest` or `HARD_BLOCKED_ACTIONS` guards and are explicitly read-only/advisory with no persistence route to any provider.
3. **Plan-only schema** — a Postgres table shape declared in source but, per the catalogue's own classification, not evidenced as created or executed. Provider-specific by construction (it is a Postgres DDL shape), and not to be read as AAB's canonical data model.
4. **Retired** — a Supabase action that returns HTTP 410 and does not fall back to legacy persistence.

Only tier 1 constitutes a working implementation of an operation. Tiers 2–3 are evidence of design intent, at various levels of provider-specificity, not of an available path.

## Cross-cutting findings

- **CAP-04/CAP-09 scope collision, not a vocabulary problem.** `AAB_LEARNING_MEMORY_ACTIONS` is the current Supabase bundle's only "memory"-named action group, but it realizes CAP-09's operation (trial-outcome learning), not CAP-04's (historical multi-institution scientific memory). Wiring CAP-09 as a direct wire without first resolving this risks CAP-04 later being wired into the same group by name-matching alone, which would be wrong on scope regardless of what either side's fields are called.
- **CAP-02/CAP-04 have no Supabase implementation of their operations at all — the field-name gap is a symptom of that, not a separate finding.** Confirmed against the full HTTP action field catalogue: no declared active Supabase action realizes either operation. Both also have real but disconnected scaffolding one tier down (plan-only schema for CAP-04's operation; five source adapters, all `*_NOT_CONNECTED`, for CAP-02's). Once an implementation exists — at Supabase or any other provider — its field names will differ from CAP-34's canonical names by default, exactly as they do for CAP-06/07/09 today, and that gap is adapter-layer work.
- **Even the "direct wire" capabilities need an adapter, and that is expected.** CAP-06, CAP-07 and CAP-09 each have a real Supabase implementation of their operation, but none of their evidenced field names were established as AAB's canonical vocabulary — they are Supabase's implementation detail. A thin mapping layer between CAP-34's canonical fields and Supabase's field names is assumed for all three, not a sign that the match is weaker than "direct."
- **Browser-contract maturity indicates design intent, not gateway maturity, at any provider.** CAP-01, CAP-02 and CAP-05 all have unusually well-developed tier-2 contract families whose vocabulary maps closely onto their capability's behaviour. None of that reduces the classification below "new gateway action needed" or "design decision required" — a fail-closed, non-persistent advisory contract is not a path to a working operation, only a plausible shape for one, independent of which provider eventually implements it.
